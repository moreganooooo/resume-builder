# Bullet Bank Management Menu — Design

## Problem

Rebuilding or maintaining the bullet bank means running 6 sequential
standalone scripts (`audit_bullet_bank.py` → `cluster_bullet_bank.py` →
`rewrite_bullets.py` → `audit_keepers.py` → `score_keeper_gems.py` →
`embed_bullet_bank.py`), plus two adjacent maintenance scripts
(`triage_needs_review.py`, `retire_rewrite_queue.py`) that reconcile
`needs-review.csv`/`rewrite-queue.csv` rows generated by everyday
`orchestrator.py` runs. None of this is visible in the interactive menu or
the README today — only the full from-scratch "New User? Start Here!"
bootstrap flow (`bootstrap_bullet_bank.py`) runs these in order, and that
flow also does ingestion + profile setup a returning user doesn't need.

Someone mid-rebuild (having already run one or two stages by hand) has no
way to see which stage they're on, what's next, or whether a given stage's
output is already stale relative to its input — they have to remember the
order and re-derive state by eyeballing file timestamps themselves.

## Goals

1. A new "Manage Bullet Bank" entry in the main interactive menu, opening
   a nested submenu — distinct from "New User? Start Here!", which
   remains the full ingestion+profile+6-stage flow for a first-time setup.
2. The submenu shows a status line per stage/script (never run / stale /
   up to date, with a timestamp) computed from existing file
   modification times — no new state file.
3. The submenu's 6 rebuild-stage choices are numbered in pipeline order
   directly in their labels, so "what's next" is always visible without
   needing to remember anything.
4. Running a stage/script re-enters the submenu (not the main menu)
   afterward, with status re-rendered, so a multi-stage rebuild session
   doesn't require re-navigating from the top every time.
5. A confirmation gate before any stage that makes a real Gemini API
   call (5 of the 6 rebuild stages), matching this app's existing
   cost-confirmation pattern elsewhere.
6. README documentation of the accurate stage order, inputs/outputs, and
   the new menu entry.

## Non-Goals

- No changes to any of the 8 underlying scripts themselves — each is
  invoked exactly as-is, unmodified, as a subprocess (same pattern as
  `bootstrap_bullet_bank.py`'s existing `run_stage()`).
- No exposure of per-script CLI flags (`--auto-rewrite`, `--dry-run`,
  `--limit`, etc.) through the menu — each menu action runs a script's
  plain default invocation. Anyone needing a flag still runs that script
  directly from the terminal.
- `detect_hidden_gems.py` is explicitly left out of the menu — confirmed
  with the user it's not part of their actual workflow;
  `score_keeper_gems.py` is the one real "hidden gems" stage
  (`bootstrap_bullet_bank.PIPELINE_STAGES` index 4).
- No new state-tracking file. Status is derived entirely from existing
  file mtimes (and, for the one stage that updates its file in place,
  column completeness) — see Architecture.
- No change to `bootstrap_bullet_bank.py`'s own full-flow behavior,
  `PIPELINE_STAGES`, or `_CONFIRMATION_GATES` — this is a new, separate,
  additive entry point over the same scripts, not a replacement.

## Architecture

### 1. Stage & script definitions

New module `scripts/bullet_bank_menu.py`. A `STAGES` list, one entry per
rebuild stage, in pipeline order (verified directly against each script's
own path constants, not assumed):

| # | Script | Input(s) | Output | API cost |
|---|---|---|---|---|
| 1 | `audit_bullet_bank.py` | `bullet-bank-clean.csv` | `bullet-bank-audited.csv` | Yes |
| 2 | `cluster_bullet_bank.py` | `bullet-bank-clean.csv`, `bullet-bank-audited.csv` | `bullet-bank-cluster-map.csv` | Yes |
| 3 | `rewrite_bullets.py` | `bullet-bank-cluster-map.csv` | `bullet-bank-keepers.csv` | Yes |
| 4 | `audit_keepers.py` | `bullet-bank-keepers.csv` | `bullet-bank-keepers-audited.csv` | Yes |
| 5 | `score_keeper_gems.py` | `bullet-bank-keepers-audited.csv` (in place) | `bullet-bank-keepers-audited.csv` | Yes |
| 6 | `embed_bullet_bank.py` | `bullet-bank-keepers-audited.csv` | `bullet_vectors_ge2_d768.npy` | Yes |

All paths resolved under `resume-engine/knowledge_base/`, matching every
script's own `KB_DIR` convention.

A separate `MAINTENANCE` list holds the 2 non-sequential scripts:

| Script | Watched file | Status signal |
|---|---|---|
| `triage_needs_review.py` | `needs-review.csv` | row count ("N rows waiting" / "empty") |
| `retire_rewrite_queue.py` | `rewrite-queue.csv` | count of `is_representative=False` rows still present |

### 2. Status computation

`_stage_status(stage) -> (label: str, detail: str)`:

- Stages 1, 2, 3, 4, 6 (distinct input/output files): output missing →
  `"Never run"`. Output mtime older than any input's mtime → `"Stale"`.
  Otherwise → `"Up to date"`, with the output's mtime formatted for
  display.
- Stage 5 (`score_keeper_gems.py`, in-place update — its input and output
  are literally the same file, so an mtime comparison against itself is
  meaningless): reads `bullet-bank-keepers-audited.csv` and checks whether
  `hidden_gem_score`/`hidden_gem_flag` are present and non-blank on every
  row (the same completeness check `detect_blank_scores.py` already
  performs). Any blank or missing column → `"Stale"`; fully populated →
  `"Up to date"`.

`_maintenance_status(entry)` reads row counts directly (stdlib `csv`, no
pandas needed for a maintenance-script status line).

### 3. Menu integration

`menu.py` changes are intentionally small:

- `_CHOICES` gains one new group: `questionary.Separator("── Bullet Bank ──")`
  followed by one `Choice(title=f"{theme.ICONS['bullet_bank']}  Manage Bullet Bank", value="bullet_bank")`.
  `theme.py` gains one new icon token, `bullet_bank`, in both the Nerd
  Font and Unicode icon sets (following the exact pattern the other
  category icons already use).
- `_handle_bullet_bank() -> bool` calls
  `bullet_bank_menu.run_bullet_bank_menu()` and always returns `False` —
  same convention as `_handle_polish` (no `_CHAIN` entry; the submenu is
  its own self-contained loop, not a step in the pipeline chain).
- `_HANDLERS["bullet_bank"] = _handle_bullet_bank`. No `_CHAIN` entry.

### 4. The submenu loop

`run_bullet_bank_menu()` in `bullet_bank_menu.py`:

```
loop:
  cli_art.render_bullet_bank_status(STAGES, MAINTENANCE)   # fresh every iteration
  choice = questionary.select(choices=[
    "1. Audit Bullet Bank (Score Quality)"       -> "audit"
    "2. Cluster & Classify Bullets"               -> "cluster"
    "3. Rewrite Weak Bullets"                     -> "rewrite"
    "4. Re-Audit Keepers"                         -> "audit_keepers"
    "5. Score Hidden Gems"                        -> "score_gems"
    "6. Embed Bullet Bank (Final Step)"           -> "embed"
    Separator
    "Triage Needs-Review Queue"                   -> "triage"
    "Retire Abandoned Rewrite-Queue Bullets"      -> "retire"
    "Back to Main Menu"                           -> "__back__"
  ])
  if choice in (None, "__back__"): return
  run the chosen script (confirm gate first if it's API-costing)
  # loop back -- status re-renders, reflecting whatever just happened
```

Running a script: confirm gate (only for the 5 API-costing rebuild
stages — `questionary.confirm(...)`, same style as
`bootstrap_bullet_bank._CONFIRMATION_GATES`) → declined → back to the
loop with nothing run. Confirmed (or no gate needed) → `subprocess.run([sys.executable, script_path])`
(identical pattern to `bootstrap_bullet_bank.run_stage()`) → non-zero exit
→ `cli_art.display_error(f"{script_name} exited with an error — check the output above.")`,
stay in the submenu (never auto-advances to the next stage).

`cli_art.render_bullet_bank_status()` renders a table (same visual family
as `render_fit_table` — `theme.SUCCESS` for "Up to date", `theme.WARNING`
for "Stale", dim for "Never run"), so this reads as part of the same
unified system as the rest of this redesign, not a bolted-on one-off.

### 5. Documentation

README gains a new `## Bullet Bank Management` section (placed near the
existing `## Bullet bank feedback loop` section) documenting: the 6-stage
order with each stage's exact input/output files (the table from
Architecture section 1), the new menu entry and how it differs from "New
User? Start Here!" (individual stages vs. the full ingestion+profile+
6-stage flow), and the 2 maintenance scripts' role. `CLAUDE.md` gets no
changes — this is a menu-level UX addition, not a new setup/run
requirement.

## Data Flow

```
menu._CHOICES  --"Manage Bullet Bank"-->  menu._handle_bullet_bank()
                                                |
                                                v
                                bullet_bank_menu.run_bullet_bank_menu()
                                                |
                          loop: render status -> select -> run script -> loop
                                                |
                                    "Back to Main Menu" -> return False
                                                |
                                                v
                                    menu.py's main while-loop resumes
```

## Error Handling

- Missing knowledge-base directory or any watched file: treated as
  "Never run," not an error — every stage's output path is checked with
  `os.path.exists()` first, matching every existing script's own
  `os.makedirs(..., exist_ok=True)`-style tolerance of a fresh/partial
  bank.
- A stage script exiting non-zero: reported via `cli_art.display_error`,
  submenu stays open, nothing else happens automatically — mirrors
  `run_full_pipeline`'s own "stop immediately, resume later" philosophy,
  just without auto-advancing between stages at all (each stage here is
  an explicit, individual choice every time).
- Cancelled `questionary.select`/`questionary.confirm` (Esc/Ctrl-C):
  treated as "Back"/"declined" respectively — no script runs.

## Testing

- `_stage_status()`: unit tests using temp files + `os.utime()` to control
  mtimes — missing output → "Never run"; output older than input →
  "Stale"; output newer → "Up to date". Stage 5's column-completeness
  path gets its own tests (all rows populated → "Up to date"; any blank
  → "Stale"; column entirely missing → "Stale").
- `_maintenance_status()`: unit tests over temp CSVs with known row
  counts / `is_representative` values.
- `run_bullet_bank_menu()`: unit tests mocking `questionary.select` and
  `subprocess.run` entirely (matching the existing convention — no test
  in this codebase invokes a real bullet-bank script or makes a real API
  call). Covers: choosing "Back" returns immediately without running
  anything; choosing an API-costing stage prompts for confirmation first
  and skips the subprocess call if declined; a non-zero subprocess exit
  triggers `cli_art.display_error` and the loop continues (doesn't
  raise/exit); choosing "Triage" or "Retire" runs without any
  confirmation prompt.
- Live verification: with a real (even tiny/fake) `bullet-bank-clean.csv`
  present, open "Manage Bullet Bank," confirm the status table shows
  accurate never-run/stale/up-to-date states, run one lightweight
  maintenance script (`triage_needs_review.py` against an empty
  `needs-review.csv`) end-to-end and confirm the submenu re-renders with
  updated status afterward, then confirm "Back to Main Menu" returns
  cleanly to the main loop.
