## Open / unexplained

- **Empty-stdout failure at 812 candidates** (`⚠ Liveness check produced
  unparseable output`). **Narrowed 2026-08-23, not conclusively solved.**
  Ruled OUT empirically rather than by reading: the blob is not too large
  and is not lost to buffering -- a child writing an 812-, and separately
  a 2,000-entry blob through the identical `Popen(stdout=<real file>)`
  shape lands complete and parses every time (Node's stdout to a regular
  file is synchronous).
  What surfaced instead is a real data-loss bug that *can* produce this
  signature: `LIVENESS_INPUT_PATH`/`LIVENESS_OUTPUT_PATH` were fixed paths
  shared by every sweep of a profile, and `open(path, "w")` truncates. An
  overlapping run -- or, likelier here, an orphaned Node child from a run
  killed mid-check, which the code's own comment acknowledged survives --
  clobbers a live run's output while both children exit 0. Reproduced: one
  run destroying another's results. NOT reproduced: the precise
  interleaving that leaves the reader an empty file. So this is a
  plausible mechanism, not a proven diagnosis.
  Fixed regardless -- `liveness._run_temp_paths()` gives every spawn a
  unique pair, so a stale writer can only corrupt its own dead run's file,
  and `liveness.leftover_temp_files()` makes killed-run residue visible.
  **If the symptom recurs after this, the shared path was not the cause**
  -- the next place to look is `check-liveness.mjs`'s `finally`, where the
  blob is printed after `await browser.close()`.
